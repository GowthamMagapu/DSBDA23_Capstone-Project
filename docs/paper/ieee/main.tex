\begin{abstract}
Automated resume screening is increasingly delegated to large language models,
but deployments are rarely accompanied by measurements of how they fail. We
present AgentU, a web application in which three cooperating agents automate a
small organisation's hiring workflow. An HR agent turns a company profile and a
rough role description into a public job listing, distributes it and screens
every application. A management agent moves candidates through an interview
pipeline and drafts candidate emails that the recruiter approves before sending.
An analysis agent reports each role's score distribution with confidence
intervals and flags applications whose scores should not be trusted. The system
rests on two architectural commitments: event-sourced orchestration, in which
every agent step is appended to a log that the interface projects, decoupling
progress visibility from the request and response cycle; and degradation-first
design, in which every external dependency has a documented fallback. We
evaluate the screening component on the production code path against
author-assigned ground truth on 48 job and resume pairs, comparing the language
model scorer with the system's own keyword-overlap fallback and a
reject-everyone baseline. The language model scorer reaches 81.3 percent
accuracy, a macro F1 of 0.740, a Cohen kappa of 0.623 and a Spearman rank
correlation of 0.915, against a kappa of 0.235 for keyword overlap and 0 for the
trivial rule. Every error is an over-promotion: no candidate a human would
shortlist was rejected. Four negative results are equally central. The scorer
does not see through keyword stuffing; it is stable under repetition but not
under rewording of the same facts; a one-line forged system turn moved an
unrelated candidate from 0 to 95, with 2 of 10 attacks succeeding; and scanned
documents parse successfully while yielding almost no text. The system's own
silent fallback also corrupted our first measurement run. A revised rubric
prompt that states the decision bands, asks for per-requirement evidence and
fences resume text as untrusted input raised held-out accuracy from 87.5 to 91.7
percent and kappa from 0.695 to 0.781, and blocked all ten injection attempts.
The remaining failure modes are now detected in the product itself: the analysis
agent flags fallback-scored, unreadable, injection-bearing and keyword-stuffed
applications, and every fallback is reported to the recruiter with its cause.
\end{abstract}

\section{Introduction}

\subsection{Motivation}

Recruiting at small and mid-sized organisations involves substantial repetitive
work that is adjacent to, but not the same as, judgement: rewriting a rough role
description into a presentable public listing, distributing it, collecting
applications in varied document formats, reading each resume against the same
requirements, scheduling interviews, writing to candidates, and keeping the
hiring manager informed. Applicant tracking systems address storage and
workflow, but the reading and drafting remain manual, and the informing is
typically a dashboard the recruiter must remember to visit.

Large language models are an obvious fit for the drafting and reading. What is
less obvious, and much less frequently reported, is how such a system behaves
when the model is wrong, when the model is unavailable, when the input document
cannot be read, or when the input is adversarial. A candidate has a direct
incentive to manipulate a screener, and unlike most language model
applications, the untrusted input here arrives as a file the candidate authored.

\subsection{Problem Statement}

Existing language-model-based screening systems automate a single hiring stage
and are evaluated offline for agreement with human ratings~\cite{b1,b2},
without measuring how they fail. We address two questions:

\begin{enumerate}
\item \textit{Architecturally}: how should a set of agents that perform a
multi-step, partly slow and partly failure-prone workflow report their progress
and survive the failure of their dependencies?
\item \textit{Empirically}: how well does language-model-based resume screening
agree with human judgement in this system, and, more importantly, \textit{how
does it fail}?
\end{enumerate}

\subsection{Contributions}

\begin{enumerate}
\item \textbf{A three-agent recruitment system} (HR, management and analysis
agents) covering publishing, distribution, screening, candidate coordination
and pipeline analysis in one deployment, with the recruiter as the final
decision-maker at every consequential step (Sections~\ref{sec:overview}
and~\ref{sec:implementation}).
\item \textbf{An event-sourced agent architecture} in which progress visibility
is decoupled from the request and response cycle. Each step appends an
\texttt{AgentEvent}; the recruiter's activity feed is a projection of that log,
so work deferred past the HTTP response is exactly as visible as work performed
before it (Sections~\ref{sec:eventsourcing} and~\ref{sec:boundary}).
\item \textbf{A degradation-first design} in which every external dependency has
an explicit fallback that keeps the core workflow available, and in which each
fallback is reported to the recruiter with its cause
(Section~\ref{sec:degradation}).
\item \textbf{An evaluation harness that measures the production code path}
rather than a reimplementation, together with a methodological finding: a system
that degrades silently is a hazard to its own evaluation. Our first run recorded
42 of 48 observations as model output when the model had stopped responding
(Sections~\ref{sec:protocol} and~\ref{sec:silent}).
\item \textbf{An empirical characterisation of failure modes} in language model
resume screening, including a prompt-injection vulnerability that changed a
hiring decision, sensitivity of scores to resume wording rather than substance,
and silent upstream extraction failure (Section~\ref{sec:results}).
\item \textbf{Mitigations evaluated or deployed}: a rubric prompt evaluated on
held-out data (Section~\ref{sec:v2}), and an analysis agent that turns each
measured failure mode into a per-application integrity flag
(Section~\ref{sec:analysis}).
\end{enumerate}

\subsection{Scope}

This is a capstone-scale study. The labelled dataset is 48 synthetic pairs plus
24 held-out pairs, with single-annotator ground truth, one model and one
temperature setting. Results indicate direction and support design claims; they
are not a benchmark. Limitations are stated in full in
Section~\ref{sec:ethics}.

\section{Related Work}

\textbf{Language model resume screening and multi-agent hiring.} Lo
\textit{et al.}~\cite{b1}, the base paper for this project, propose a four-agent
framework (resume extractor, evaluator, summariser and score formatter) built on
CrewAI and LangChain, in which retrieval-augmented generation supplies the
evaluator with external criteria such as certifications, university rankings and
company-specific hiring criteria. On 105 anonymised online resumes rated by HR
professionals, the retrieval-augmented configuration with DeepSeek-V3 reached a
Pearson correlation of 0.84 on the top 10\,\% of candidates and a mean absolute
error of 0.90, outperforming single-model baselines. Gan \textit{et
al.}~\cite{b2} use language model agents to summarise and grade resumes,
reporting screening 11 times faster than manual review and an F1 of 87.73\,\%
for resume sentence classification after fine-tuning. Filatova \textit{et
al.}~\cite{b3} describe a modular multi-agent hiring assistant with document and
video preprocessing, public-data verification, fit scoring with risk penalties
and human-in-the-loop validation; on 64 applicants for a backend role it needed
1.70 hours per qualified candidate against 3.33 hours for an experienced
recruiter. MLAR~\cite{b4} embeds three language model layers (job-posting
features, resume parsing and semantic matching) in a robotic process automation
applicant tracker and processes a resume in 5.4~s on a 2400-resume benchmark.
General multi-agent frameworks such as AutoGen~\cite{b5} structure language model
applications as conversations between customisable agents. Work on language
models as judges~\cite{b6} shows that a strong model can exceed 80\,\% agreement
with human preferences, the level of agreement between humans, while exhibiting
position, verbosity and self-enhancement biases.

AgentU follows the evaluation logic of~\cite{b1}, agreement with human judgement
rather than raw accuracy, but departs from it in three ways. Its screening step
is deliberately a single model call with a deterministic fallback, so that
determinism and injection effects can be attributed to one component; its
agentic behaviour lies in workflow orchestration rather than in scoring. It
covers the stages before and after screening: publishing, distribution,
interviews and candidate email. And where~\cite{b1,b2,b3,b4} evaluate accuracy
or speed, we measure determinism, presentation sensitivity, adversarial input and
extraction failure on the code path that runs in production.

\textbf{Algorithmic hiring, bias and ethics.} The best-known cautionary case is
Amazon's internal recruiting tool, abandoned after it was found to disadvantage
women~\cite{b7}. Bogen and Rieke~\cite{b8} survey where bias enters the hiring
funnel, and Raghavan \textit{et al.}~\cite{b9} find that vendors of
pre-employment assessments disclose little about how their models are validated
or de-biased. K\"ochling and Wehner~\cite{b10} systematically review
discrimination in algorithmic HR decisions, and Hunkenschroer and
Luetge~\cite{b11} map the ethical risks of AI-enabled recruiting, including
bias, privacy, transparency and accountability. Fabris \textit{et
al.}~\cite{b12} survey systems, bias measures, mitigation strategies, datasets
and law, concluding that whether algorithmic hiring is less biased than low-tech
alternatives remains open. Audits of language model screeners confirm the
concern: Armstrong \textit{et al.}~\cite{b13} find stereotype-based race and
gender bias in GPT-3.5's resume ratings, and Wilson and Caliskan~\cite{b14} find
that embedding-based screening favoured White-associated names in 85.1\,\% of
cases and female-associated names in only 11.1\,\%.

\textbf{Regulation.} New York City Local Law 144~\cite{b15} requires independent
bias audits of automated employment decision tools and notification of
candidates. The European Union Artificial Intelligence Act~\cite{b16} classifies
AI systems used in recruitment and worker management as high-risk. Both are
directly relevant to a system of this shape (Section~\ref{sec:ethics}).

\textbf{Prompt injection and defences.} Perez and Ribeiro~\cite{b17} showed that
handcrafted inputs can hijack GPT-3's goal. Greshake \textit{et al.}~\cite{b18}
describe indirect prompt injection, in which the attack arrives inside data the
application ingests; this is exactly our threat model, since the resume is
candidate-authored. The OWASP Top 10 for Large Language Model
Applications~\cite{b19} lists prompt injection as LLM01. Defences include
benchmark-driven boundary awareness and explicit reminders~\cite{b20},
spotlighting (delimiting, datamarking or encoding untrusted text), which reduced
attack success from over 50\,\% to under 2\,\%~\cite{b21}, and structured
queries that separate prompt and data channels through fine-tuning~\cite{b22}.
Baxi \textit{et al.}~\cite{b23} study injection in r\'esum\'e screening
specifically, finding that injected self-promotion helps most when few
candidates use it and candidates are of similar quality.

\textbf{Agreement metrics.} Cohen's $\kappa$~\cite{b24} corrects observed
agreement for agreement expected by chance, which Section~\ref{sec:metrics}
argues is essential under our class imbalance. The analysis agent reports band
shares with Wilson score intervals~\cite{b25}, which behave well at the small
sample sizes of a single role.

\textbf{Gap.} The reviewed work either scores resumes offline~\cite{b1,b2,b3,b4},
or studies bias~\cite{b13,b14} and injection~\cite{b17,b18,b23} in isolation
from a working system. Fine-tuning defences~\cite{b22} are not available to a
system built on a hosted model interface. We found no work that reports, for one
deployed recruitment system, the combination of screening quality, determinism,
presentation sensitivity, adversarial robustness and upstream extraction
reliability on the production code path, and that feeds those measurements back
into in-product detection.

\section{System Overview}
\label{sec:overview}

A recruiter signs up, describes their company once, and publishes a role. Three
agents then share the work.

\textbf{HR agent.} It drafts a polished public listing from the company profile
and the raw role description; publishes it at a public careers URL with
\texttt{JobPosting} structured data for Google for Jobs, lists it in the
sitemap, notifies the Google Indexing API and shares it to LinkedIn, Discord and
Telegram where configured; emails the recruiter that the job is live; screens
each incoming application, producing a score, a written evaluation and matched
and missing skill lists, and emails the recruiter with the result; and
optionally re-scores the recruiter's existing candidate pool against the new
role.

\textbf{Management agent.} It moves each candidate through a pipeline (Applied,
Shortlisted, Interview, Offer, Hired, Rejected) that is stored separately from
the AI decision band; schedules interviews in the recruiter's time zone and
records 1--5 feedback with notes; and drafts interview, offer and rejection
emails with the language model, which the recruiter edits and confirms before
each one is sent, with replies going to the recruiter.

\textbf{Analysis agent.} It reports the score distribution of a role, band
shares with 95\,\% confidence intervals and a sample-size caveat, and flags
applications whose scores should not be taken at face value.

Every step above is recorded in an activity feed the recruiter can watch. The
system is deployed on Vercel with a MySQL-compatible TiDB Cloud database.

\section{Methodology and System Design}

\subsection{Layered Architecture}

The application is a single Next.js 15 deployment with six layers: client pages,
a request gate implemented as middleware, 19 route handlers, a 27-module service
layer, an object-relational mapper over MySQL, and the external services for
language modelling, professional-network posting and electronic mail, plus the
optional Google Indexing, Discord and Telegram channels. Business logic lives in
the service layer, not in route handlers, so it can be exercised directly; the
evaluation harness (Section~\ref{sec:protocol}) and the unit tests
(Section~\ref{sec:testing}) import the same functions the application runs.

\subsection{Event-Sourced Agent Orchestration}
\label{sec:eventsourcing}

The design problem is that the agents' work is multi-step, partly slow and
partly failure-prone, while HTTP offers a single response. Returning a summary
at the end would make everything before it invisible and everything after it
unreportable.

Instead, each step appends an \texttt{AgentEvent} row holding a type, a level, a
message, the owner, an optional job and a timestamp, and the recruiter's
activity feed is a projection of that log, polled with a cursor every five
seconds. Three consequences follow.

\begin{itemize}
\item \textbf{Progress visibility is decoupled from the response.} A step that
runs after the response is as visible as one that runs before it.
\item \textbf{Logging cannot break the workflow it describes.} The logging
function swallows its own errors; a failure to record a step must never fail
the step.
\item \textbf{The log is the audit trail.} The levels info, success, warning and
error let the feed distinguish ``the post was skipped because you are not
connected'' from ``the network rejected the post''. Management actions (stage
moves, interviews, feedback and emails) are mirrored into the same log.
\end{itemize}

\label{sec:degradation}

Section~\ref{sec:silent} reports the cost of a silent fallback: one that is
invisible to the user is also invisible to the evaluator. That finding changed
the design. The screening fallback now returns the reason the model call failed,
with any interface key redacted; the application route and pool re-scoring post
it to the feed as a warning; and the analysis agent flags every application that
carries no AI evaluation (Section~\ref{sec:analysis}).

\subsection{Work Placement at the Response Boundary}
\label{sec:boundary}

Work is placed on one side or the other of the HTTP response deliberately.

On the publish path, listing generation and the professional-network post run
in-request because their outcome belongs in the response; the confirmation email
and candidate-pool re-scoring run in a deferred hook, since the recruiter should
not wait for a pool of 100 candidates to be re-scored. Pool scoring is bounded
at a concurrency of three, so a large pool cannot fan out into an unbounded
burst of concurrent model calls.

On the application path the split is different: extraction and scoring run
in-request, because the score must exist before the row is written, and only the
recruiter email is deferred. The applicant therefore waits on a third-party
model, measured at a median of 1335~ms (Section~\ref{sec:extraction}).

\subsection{Security Measures}

\begin{itemize}
\item \textbf{Input validation.} Schema validation at every trust boundary;
uploads constrained by an extension allowlist (PDF, DOC, DOCX, RTF, TXT) and a
4~MB cap, set by the hosting platform's 4.5~MB request-body limit.
\item \textbf{Ownership.} Every authenticated route resolves the session user
identifier and filters by it. Enforcement is per query rather than by a database
policy, a limitation noted in Section~\ref{sec:ethics}.
\item \textbf{Rate limiting.} The public application endpoint allows five
submissions per client address per 15 minutes, using an in-memory fixed window.
\item \textbf{Credentials at rest.} Professional-network access tokens are
encrypted with AES-256-GCM under a key derived from the application secret;
rotating that secret invalidates stored tokens and forces a reconnect.
\item \textbf{Authentication.} Session tokens are issued as JSON Web Tokens,
passwords are hashed with bcrypt, and federated sign-in is optional.
\item \textbf{Prompt injection.} The production prompt (v2) fences the resume
between delimiters that are stripped from candidate text and tells the model to
ignore instructions inside them (Section~\ref{sec:v2}). The candidate-email
drafter likewise treats the candidate name and recruiter note as data. The
analysis agent additionally flags instruction-like text in a resume
(Section~\ref{sec:analysis}).
\end{itemize}

\subsection{Data Model}

Ten models are defined, with the user as the tenant root. One asymmetry is
deliberate: deleting a recruiter cascades to their jobs, applications, company,
professional-network connection and event history, but candidate profile rows
survive with a null owner, so candidate records outlive the recruiter who
collected them. Section~\ref{sec:ethics} discusses the data-protection
implications.

The candidate profile is inserted or updated by email address on every
application, accumulating a reusable talent pool that later roles can be scored
against. This is the mechanism behind the optional pool re-scoring described in
Section~\ref{sec:boundary}. The management agent adds six columns to the
application: its pipeline stage, when the stage last changed, the interview time
and link, and a feedback rating and notes. The pipeline stage is stored
separately from the AI decision band, so a recruiter's decision never overwrites
the model's recorded judgement.

\subsection{The Screening Pipeline}

The extraction function dispatches on file type, using a PDF parser for portable
documents, a DOCX reader for word-processor documents and a UTF-8 decode for
plain text and RTF, and returns an empty string for anything unrecognised,
including legacy binary DOC files, which are therefore scored on the cover letter
alone. The extracted text is concatenated with the cover letter and capped at
20\,000 characters, of which the first 12\,000 are sent to the model.

The analysis function sends this text together with the job title and
requirements to the language model under a system instruction demanding strict
JSON, and maps the returned score to a decision band. At least 70 is
\texttt{selected}, at least 40 is \texttt{review}, and anything lower is
\texttt{rejected}. The intermediate \texttt{review} band is deliberate: it
routes uncertain cases to a human rather than resolving them automatically.
Scores are advisory; the system never rejects a candidate on its own.

The production system instruction is prompt v2, which states the scoring rubric,
asks for per-requirement evidence and fences the resume as untrusted text
(Section~\ref{sec:v2}); Sections~\ref{sec:accuracy} to~\ref{sec:silent} measure
the original prompt, v1, which asked only for a score from 0 to 100. Any
exception is caught and a keyword fallback, the fraction of distinct requirement
terms (lower-case tokens of three or more characters) that appear in the resume,
is returned instead, with an empty summary and the failure reason.

\subsection{The Management Agent}

The management agent coordinates candidates for the selected role through
owner-only routes that mirror every action into the activity feed.

\begin{itemize}
\item \textbf{Pipeline.} A six-column board (Applied, Shortlisted, Interview,
Offer, Hired, Rejected). Applications created before the pipeline existed read
as Applied.
\item \textbf{Interviews.} The recruiter sets a date, time and meeting link;
times are formatted in the recruiter's time zone, since the server runs in UTC,
and the candidate moves to Interview.
\item \textbf{Feedback.} A rating from 1 to 5 and free-text notes per candidate.
\item \textbf{Candidate email.} The language model drafts an interview
invitation, rejection or offer from the facts provided, under an instruction
never to invent salaries, dates, links or names. If the model is unavailable, a
complete template is used instead. The recruiter edits and confirms every draft
before it is sent, so the AI never emails a candidate on its own, and replies go
to the recruiter's address.
\end{itemize}

\subsection{The Analysis Agent}
\label{sec:analysis}

The per-application scorer answers how good a candidate is. The analysis agent
answers two different questions over a whole role: what the score distribution
looks like and how much of it should be believed, and where the screening itself
probably went wrong. Its statistical and integrity passes are pure and
synchronous, with no database access and no model calls, so they are fully
unit-tested.

\textbf{Statistics.} The agent reports the median, mean, standard deviation,
range and interquartile range with a plain-language reading of the spread; band
shares with 95\,\% Wilson score intervals~\cite{b25}; and a sample-size caveat
(fewer than 5 applications: descriptive only; fewer than 15: low; fewer than 40:
moderate; otherwise reasonable). Rule-based recommendations and bottleneck notes
summarise the most common missing skills.

\textbf{Integrity flags.} Each detector, listed in Table~\ref{tab:flags},
corresponds to a failure mode measured in Section~\ref{sec:results} and uses the
evaluation's own thresholds. Each injection pattern needs both a verb and an
object to fire, so a resume that merely contains ``override'' or begins a line
with ``Systems:'' does not trip it. Flagged applications are listed errors
first, so the recruiter reads the least trustworthy scores first.

\subsection{Testing}
\label{sec:testing}

The pure functions are covered by a unit-test suite of 163 tests in 42 suites
across 13 test files, including 46 tests for the analysis agent and 12 for the
management agent. All 163 pass.

\section{Experimental Setup}

The full protocol, harness and raw observations are kept with the source code.

\subsection{Apparatus}

All experiments call the \textit{production functions} used for analysis,
keyword fallback and text extraction, so measurements describe shipped behaviour
including its fallbacks rather than an idealised reimplementation. The model was
Gemini 3.5 Flash Lite at temperature 0.2 in JSON response mode. The main run
completed on 18 September 2026, consuming 97 billable interface calls over 578~s
of wall-clock time; the prompt v2 runs completed on 30 October 2026. Requests
are throttled to ten per minute and results are cached by input hash, so
re-running a report costs no quota. The deployed application reads its model
from configuration; results here apply to the evaluated model.

\subsection{Dataset}

Three tiers support different claims.

\textbf{Synthetic tier.} Twelve authored resumes across four job specifications
give 48 labelled pairs. Each pair carries a categorical human label and an
ordinal human fit rating from 0 to 4, used for rank correlation. The roles are
J1 Frontend Engineer (React and TypeScript), J2 Backend Engineer (Node.js and
PostgreSQL), J3 Machine Learning Engineer (NLP) and J4 Cloud Infrastructure
Engineer (AWS and Kubernetes). Resumes span clear fits, clear non-fits and
borderline cases, and include two adversarial constructions:

\begin{itemize}
\item \textbf{R06, the keyword stuffer}, lists nearly every term in all four job
specifications while declaring no professional experience. It is labelled
\texttt{rejected} for all four roles and separates semantic judgement from
lexical overlap.
\item \textbf{R07, the vocabulary mismatch}, has five years of
component-library, performance and accessibility depth in Vue rather than React,
applying to the React role. It is labelled \texttt{review} and tests whether
transferable experience survives unfamiliar vocabulary.
\end{itemize}

The label distribution is 36 rejected, 6 review and 6 selected. Authoring rather
than collecting resumes is a deliberate trade-off: it permits controlled
adversarial cases and avoids processing real applicants' personal data, at the
cost of realism.

\textbf{Held-out tier.} Six further authored resumes against the same four jobs
give 24 labelled pairs (19 rejected, 3 review, 2 selected), written and labelled
under the same rules \textit{before} prompt v2 was run. It measures whether a
prompt change made after studying the synthetic tier's errors generalises beyond
them.

\textbf{Real tier.} Seven self-authored tailorings of one candidate's resume, as
PDFs, are kept out of the shared dataset because they contain personal data. One
candidate cannot support an accuracy claim and none is made. It supports a
consistency claim: all seven describe the same person, education and projects,
so a screener should score them similarly for a given role.

\subsection{Conditions}

Three conditions are compared. \texttt{gemini} is the production AI scorer.
\texttt{keyword} is the production fallback, requirement-term overlap, which is
deterministic and needs no network. \texttt{majority} rejects every candidate
and marks the floor set by class imbalance. Every \texttt{gemini} result in
Sections~\ref{sec:accuracy} to~\ref{sec:silent} uses screening prompt v1;
Section~\ref{sec:v2} compares v1 with prompt v2 on both labelled tiers.

\subsection{Metrics}
\label{sec:metrics}

We report accuracy, macro F1, Cohen's $\kappa$~\cite{b24}, and Spearman's
$\rho$ between score and the human fit rating.

Accuracy alone is inadequate here. With 36 of 48 pairs labelled
\texttt{rejected}, a classifier that rejects everyone scores 75\,\%. We therefore
report $\kappa$, which corrects for chance agreement, and macro F1, which weights
the two minority classes equally with the majority. Spearman's $\rho$ is
reported because a shortlist depends on \textit{ordering} candidates correctly,
independently of whether absolute scores are calibrated.

\subsection{Protocol and the Silent-Degradation Hazard}
\label{sec:protocol}

Experiments E1 to E5 cover accuracy, determinism, variant consistency,
prompt-injection robustness and extraction reliability
(Section~\ref{sec:results}).

The harness includes a safeguard motivated by the incident in
Section~\ref{sec:silent}. Because the analysis function returns fallback scores
on any error, a quota exhaustion mid-run would otherwise be invisible in the
data. The harness detects fallback output by its empty summary, trips a breaker
after three consecutive degraded calls, probes the interface directly to report
the cause, refuses to write a partial report, and never caches a degraded
observation. Cache keys include the model identifier, so results are never
served across models.

\subsection{Determinism}

Eight pairs were scored in three trials each, with caching disabled, at
temperature 0.2. There were no decision-label flips (0 of 8). The mean
within-pair standard deviation was 0.36 (maximum 2.89) and the mean range 0.63
(maximum 5). Six of the eight pairs returned identical scores across all three
trials. Non-determinism is not a practical threat to decision stability at this
temperature: an unchanged application resubmitted receives the same outcome.

\subsection{Silent Degradation as a Measurement Hazard}
\label{sec:silent}

Our first measurement run produced apparently plausible results: 79.2\,\%
accuracy and $\kappa = 0.433$. They were invalid. The configured model's free
tier permitted 20 requests per day, which was exhausted six calls into a 48-pair
run. The analysis function caught each subsequent rate-limit error and returned
keyword-fallback scores, so 42 of 48 observations recorded the fallback under an
AI label. The corruption was detectable only because the AI and keyword
conditions returned suspiciously identical scores on several pairs.

The property that makes the system resilient in production, never failing
loudly when the model is unavailable, made it hazardous to measure, and it would
equally mislead a recruiter. Two responses followed. In the harness, fallback
output is detected, a circuit breaker stops the run, and no report mixing model
and fallback observations is written (Section~\ref{sec:protocol}). In the
product, the fallback now carries its cause into a warning event, and the
analysis agent marks fallback-scored applications as not scored by the AI
(Sections~\ref{sec:degradation} and~\ref{sec:analysis}).

\subsection{Intervention: A Rubric Prompt}
\label{sec:v2}

The errors above share a cause visible in the prompt itself. Prompt v1 asks for
a score from 0 to 100 for overall match strength but never says what the 40 and
70 cutoffs mean, so partial matches drift to about 45 and land in
\texttt{review}: seven of the nine errors, including all four keyword-stuffer
pairs, were rejected candidates scored 45 to 52. Prompt v2 makes three changes.

\begin{enumerate}
\item \textbf{A rubric aligned to the bands.} A score of 70 to 100 meets every
core requirement, including any stated minimum years; 40 to 69 has one
significant gap; 0 to 39 lacks several core requirements or any professional
experience in the role's area. Two explicit caps apply: no professional
experience in the area scores at most 39, and fewer than the stated minimum
years at most 69. A skill counts only when the resume shows it used in
professional work.
\item \textbf{Evidence before the score.} The model lists each core requirement
with a short piece of evidence and a met, partial or missing verdict, then gives
the score.
\item \textbf{Untrusted-input fencing.} The resume is wrapped in delimiters that
are stripped from the candidate's text, so a resume cannot close its own block,
and the model is told to ignore any instruction inside them. This is a form of
the delimiting defence evaluated in~\cite{b21}.
\end{enumerate}

Because v2 was written after studying the synthetic tier's errors, its score on
that tier is optimistic. We therefore wrote the held-out tier before running v2
and report both prompts on it, in Table~\ref{tab:heldout}.

On held-out data v2 makes two errors against v1's three, and it removes v1's
only two-band error: H05, an NLP graduate with academic projects but no industry
role, scored 75 and was selected under v1, and is rejected under v2. Both
remaining errors are one-band over-promotions. With 24 pairs a single decision
moves accuracy by 4.2 points, so the held-out improvement is directional rather
than conclusive.

On the synthetic tier v2 classifies all 48 pairs correctly ($\kappa = 1.000$,
$\rho = 0.882$), including the keyword stuffer R06, scored 0 in all four roles
against 45 under v1, and the vocabulary-mismatch case R07, scored 50 and
reviewed, matching the human label. This is the expected effect of fixing the
errors that motivated the rubric and is not evidence of generalisation; the
held-out figure is the honest estimate. Rank correlation falls slightly, from
0.915 to 0.882, because v2 scores most clear rejections at 0, discarding the
ordering among them that v1 retained.

Re-running the five injection attacks on the same two bases under v2 gave a
success rate of 0 of 10, against 2 of 10 under v1, with a mean score change of
2.0 (SD 4.2) against 11.4 (SD 30.4). The forged system turn that moved R09 from
0 to 95 now leaves it at 0. Two attacks still raised R08 from 55 to 65, below
the 20-point success threshold and without changing the decision, so fencing
reduces the model's responsiveness to injected text but does not remove it.

Production now uses v2. Prompt v1 remains selectable in the harness, so every
v1 result stays reproducible. Determinism and presentation sensitivity were not
re-run under v2.

\subsection{Deployment Observation}

In a live trial of the deployed system, a role received two real applications,
scored 65 and 54 percent, both in the \texttt{review} band. The analysis agent
flagged the second as not scored by the AI: its model call had failed and the
keyword fallback had produced the score. Before the changes described in
Sections~\ref{sec:degradation} and~\ref{sec:analysis}, that number would have
been presented to the recruiter as an AI judgement. Two applications support no
statistical claim; the observation shows only that the detector fires on real
traffic.

\section{Discussion}

\textbf{The evaluation is the contribution as much as the system is.} The
architecture is defensible, but the results that matter are the four negative
ones. A system that reported only its accuracy would look finished; the
stuffing, rewording, injection and extraction results show it was not.

\textbf{Measured failure modes should become product features.} Each failure the
evaluation measured now has a counterpart in the running system: the rubric
prompt for stuffing and injection, a warning event for silent fallback, and an
analysis-agent flag for each of the four. Detection is not the same as
prevention, since a flagged scanned PDF is still unreadable, but it moves the
failure from invisible to visible, which is what a human in the loop needs.

\textbf{Failure direction is a design property worth engineering for.} The
result that no strong candidate was missed and every error was an
over-promotion follows from the three-band decision scheme, not from model
quality. A two-band accept or reject scheme with the same scores would have
rejected candidates a human wanted. Systems that make consequential decisions
about people should be designed so that their errors land on the recoverable
side, and an explicit route-to-a-human band is a cheap way to obtain that.

\textbf{Stating the decision rule is cheap and effective.} Most of v1's errors
came from a prompt that asked for a score without saying what the score would be
used for. Writing the labelling policy into the prompt improved every agreement
metric on held-out data at no engineering cost. A screener's thresholds and its
instructions should be designed together.

\textbf{Presentation sensitivity may be the most consequential finding.}
Injection requires a deliberate attacker, and a known technique, delimiting
untrusted input, blocked every attack we tried. Wording sensitivity affects
every honest candidate: the same person gets different outcomes depending on
which tailoring of their resume they submit. This rewards candidates who can
afford to optimise presentation, and no mitigation we implemented addresses it.

\textbf{Silent fallback trades observability for availability.} The fallback is
right for production, but the same mechanism corrupted our measurements and
would mislead a recruiter. The resolution was not to remove the fallback but to
make it visible, and the deployment observation shows the result on live
traffic.

\section{Ethics and Limitations}
\label{sec:ethics}

\subsection{Ethical Considerations}

This system ranks people for employment. The following points are stated
plainly rather than deferred.

\begin{itemize}
\item \textbf{No fairness audit was performed.} We did not test for disparate
performance across gender, ethnicity, age, nationality, disability or
educational background, and we make no fairness claim. Audits of comparable
screeners have found such bias~\cite{b13,b14}. A fairness audit is a
prerequisite for any real deployment; in New York City a bias audit would be
legally required~\cite{b15}, and the European Union classifies employment AI as
high-risk~\cite{b16}.
\item \textbf{Human in the loop.} Scores are advisory. The \texttt{review} band
routes uncertain cases to a person, and no strong candidate was auto-rejected.
The system never moves a candidate through the pipeline or emails them without
the recruiter's action and confirmation.
\item \textbf{Exploitability.} Prompt injection is a fairness problem as much as
a security one: it advantages candidates who know the technique. Prompt v2
blocked the attacks we tested, but not an adaptive attacker.
\item \textbf{Silent misjudgement.} The scanned-PDF failure and the legacy DOC
gap disadvantage candidates whose documents the system cannot read, plausibly
correlated with access to technology. They are now flagged, not fixed.
\item \textbf{Candidate data.} Resumes are stored in the database with no
retention policy, no candidate deletion endpoint and no consent record.
Candidate profiles survive deletion of the recruiter who collected them, so
candidate data can outlive the relationship that justified collecting it. Under
India's Digital Personal Data Protection Act or the European Union's General
Data Protection Regulation this would need to be addressed before deployment.
\item \textbf{Transparency.} Candidates are not told on the application page
that their application is screened by an AI model.
\end{itemize}

\subsection{Threats to Validity}

\begin{itemize}
\item \textbf{Single-annotator ground truth.} Labels were assigned by the
authors, with no second annotator and therefore no inter-annotator agreement
statistic. Some labels are arguable, R07 in particular, where \texttt{review}
versus \texttt{selected} is a defensible judgement call.
\item \textbf{Authored resumes and authored labels.} The same authors wrote the
resumes and the labels. Synthetic resumes are cleaner and more internally
consistent than real ones, so accuracy here is likely optimistic.
\item \textbf{Small sample.} There are 48 pairs with six instances each of the
two minority classes. Per-class precision and recall for \texttt{review} and
\texttt{selected} rest on very few observations, and confidence intervals would
be wide. We report no significance tests; the sample does not support them.
\item \textbf{One model and one temperature.} There is no comparison across
models or settings, and the deployed application's model is configurable and may
differ from the evaluated one.
\item \textbf{One candidate in the real tier}, supporting consistency claims
only.
\item \textbf{Non-stationary dependency.} The scorer calls a hosted model that
may change beneath a fixed version string. Run date and model identifier are
recorded in every report.
\item \textbf{Small adversarial set.} Five attack patterns on two bases. A 20
percent success rate on this set establishes that the vulnerability was real,
not its prevalence under a broader attack surface. Likewise, v2's 0 of 10 shows
the mitigation works against these attacks, not against an adaptive attacker.
\item \textbf{Prompt revised against the test set.} Prompt v2 was written after
inspecting the synthetic tier's errors, so its perfect score there is not a
generalisation estimate. The held-out tier mitigates this, but its resumes and
labels were written by the same authors, and with 24 pairs and five
minority-class instances it is smaller still.
\item \textbf{Latency is not comparable across runs.} Median uncached latency
ranged from 2.3 to 6.9~s between runs on the same day, so we make no latency
claim for v2.
\item \textbf{Detectors are not evaluated.} The analysis agent's integrity
flags reuse the evaluation's thresholds, but their own precision and recall on
real traffic have not been measured.
\end{itemize}

\section{Future Work}

The following items are ordered by what the results indicate is most urgent.

\begin{enumerate}
\item \textbf{Read scanned documents.} Add optical character recognition for
image-only PDFs and text extraction for legacy DOC files, so flagged
applications can be scored rather than only flagged.
\item \textbf{Reduce presentation sensitivity.} Test whether extracting
structured fields before scoring, or averaging across several prompt framings,
narrows the spread; re-run the determinism and rewording experiments under
prompt v2.
\item \textbf{Conduct a fairness audit.} Construct matched resume pairs that
differ only in signals correlated with protected attributes and measure score
differences.
\item \textbf{Broaden injection testing.} Test a larger and adaptive attack set,
hidden-text variants inside real PDFs, and scoring from extracted structured
fields rather than raw text.
\item \textbf{Evaluate the analysis agent.} Measure the precision and recall of
each integrity flag on a labelled set of real applications.
\item \textbf{Strengthen the evaluation.} Add a second annotator with
inter-annotator agreement, real anonymised resumes, a larger and more balanced
label set, and a comparison across models.
\item \textbf{Engineering and governance.} Replace the in-memory rate limiter
with a shared store for multi-instance deployment, move resume files to object
storage, normalise the JSON-in-text columns, add integration tests, and add a
retention policy, candidate deletion and an AI-screening notice on the
application page.
\end{enumerate}

\section{Conclusion}

We presented AgentU, a language-model-assisted recruitment system in which HR,
management and analysis agents share one event-sourced log and every external
dependency degrades gracefully, and we evaluated its screening component against
human ground truth, a lexical baseline and a trivial baseline.

The screening component agrees substantially with human judgement
($\kappa = 0.623$, $\rho = 0.915$), decisively outperforms both baselines on
metrics robust to class imbalance, never missed a candidate a human would
shortlist, and is stable under repetition. It also failed in four ways we
characterise precisely: it did not see through keyword stuffing, it gave the
same candidate different decisions across rewordings of identical facts, it was
exploitable by a one-line prompt injection that changed a hiring outcome, and it
silently scored scanned resumes as empty. The fallback that makes the system
resilient also made it opaque, which corrupted our own first measurement run.

A rubric prompt addresses part of this: on held-out pairs written before it was
run, it raised accuracy from 87.5 to 91.7 percent and $\kappa$ from 0.695 to
0.781, removed the only two-band error, and blocked all ten injection attempts.
The rest is now visible to the recruiter: every fallback is reported with its
cause, and the analysis agent flags each measured failure mode on the
application where it occurs. Presentation sensitivity and unreadable documents
remain open.

For systems that make consequential decisions about people, we argue that
characterising failure modes is not an appendix to the evaluation but the
substance of it, and that each measured failure should become something the
system can show its user.
